# pymetadata-core 0.1.0

The first release. `pymetadata-core` reads and writes COMBINE archives (OMEX, a zip file which holds a `manifest.xml`) lazily, in Rust, and ships in three forms from one source:

- the python wheel `pymetadata-core` (module `pymetadata_core`), built for linux (x86_64, aarch64), macOS (arm64, x86_64) and windows (x64) as a single abi3 wheel per platform, python 3.11 and newer, plus an sdist;
- the npm package `@matthiaskoenig/pymetadata-core`, a WebAssembly module of 394 kB (168 kB gzipped) which imports nothing, with a small JavaScript loader and no dependency;
- the Rust crate `pymetadata-core`, which is not published to crates.io in this release.

Nothing is read or inflated before it is asked for. Opening an archive parses its central directory and the manifest and nothing else, an entry is inflated when it is requested, and writing copies every member which did not change as the compressed blob it already is.

## What it is worth

Measured against `pymetadata` 0.8.3 on the four archives of the test corpus, with the harnesses in this repository (`BENCHMARKS.md`, the machine and the protocol are described there). For the 1.4 MB archive `iCGB21FR.omex`:

| operation | pymetadata | pymetadata-core | factor |
| --- | --- | --- | --- |
| write an archive unchanged (`Omex.to_omex` against a raw copy) | 230 ms | 0.151 ms | about 1520x |
| read the manifest | 0.197 ms | 0.078 ms | 2.5x |
| read every entry | 18.6 ms | 10.3 ms | 1.8x |
| write with every entry deflated again (level 9) | 230 ms | 126 ms | 1.8x |

The write factor is large because `pymetadata` deflates every entry again on every write, while the core copies the compressed bytes. The like for like number is the recompression, where both sides do the same work: 1.8x against `Omex.to_omex` at level 9, 1.6x against `zipfile` at level 6. Reading every entry is 1.2x to 4.5x over the four archives. These are timings of one machine and no test asserts them.

## Writing

A raw copy preserves the compressed bytes of a member, its CRC, its sizes, its compression method, its MS-DOS modification time and its unix mode, so reading an archive and writing it back changes none of them. Extra fields of a member, such as an Info-ZIP extended timestamp, are not copied. Bytes in front of the archive, such as a self-extracting stub, are read but dropped on write. A member the core compresses itself (the manifest and every entry a caller sets) carries the zip epoch and mode 644, so a write is deterministic.

## Limitations of 0.1.0

- The browser has no password. `omex_open` takes none, so an archive protected with ZipCrypto cannot be opened in the browser. Python opens it with `Archive.from_bytes(data, password)`. Writing a ZipCrypto archive stores its members as plaintext, and a WinZip AES member is refused as unsupported.
- The browser sets no budget of its own and inherits the 1 GiB inflate cap of the core: a member which declares more is refused with an `OmexError` of kind `refused`. A member under the cap which the instance cannot allocate traps, and the instance is spent: every later call throws `spent`, and the page creates a new runtime.
- An `Archive` shared between python threads raises `ArchiveBusyError` while another thread inflates an entry, sets an entry or writes. Use one `Archive` per thread.

## Differences from pymetadata

`pymetadata` rewrites an archive on the way through its temporary directory, the core keeps what the archive says. Anyone who replaces `pymetadata.omex` with this package will meet three differences:

- A manifest entry without a zip member is kept, as an entry without bytes. `pymetadata` drops it, because its manifest is built from the extracted files.
- Files which the manifest does not list are kept in the order of the zip. `pymetadata` sorts them by location, after the listed entries.
- The format declared for `.` and `./manifest.xml` is kept as the archive has it. `pymetadata` always writes its own default.
