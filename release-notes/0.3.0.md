# pymetadata-core 0.3.0

Five calls a host asked for after `pymetadata` 0.9.0 swapped its COMBINE archive onto this core. Each one exists because the host had to do more work than the archive requires, or had to guess something the core knew.

- `Archive.head(location, limit)` reads the first bytes of an entry and stops there, where `entry_bytes` inflates the whole member. It is how the format of a member is told from its content.
- `has_manifest(path)` answers whether a file is a COMBINE archive from its central directory alone. It reads the end of the file and that directory, inflates nothing, and decrypts nothing.
- `Archive.set_entry_format(location, format, master)` changes the manifest entry of an existing location and leaves its content alone, where `set_entry` takes the bytes and so inflates and deflates a member whose content does not change.
- `Archive.reorder_entries(order)` lays the locations it is given into the slots those entries hold, so a host which keeps an order of its own decides the order of the written manifest and of the members behind it.
- One exception class per kind of failure: `MalformedError`, `RefusedError`, `UnsupportedError`, `NotFoundError` and `PasswordError`, each a subclass of `OmexError` and so of `ValueError`. A host no longer reads the kind off the start of a message.

## Why

`pymetadata` 0.9.0 reproduced its public behaviour on this core and kept a list of what the core made expensive. All five entries of that list are here.

The two measured ones, from `BENCHMARKS.md`, five runs of the Rust harness, the minimum published, both columns from the same session:

- Classifying every member of `iCGB21FR.omex` (1.4 MB, 24 entries) by its first 256 bytes takes 0.1350 ms with `head` against 10.1016 ms with `entry_bytes`, a factor of 75. The factor grows with the archive, because the head is bounded and the inflate is not: it is 2.1x for the 7 kB fixture and 22x for the 1.1 MB one.
- Asking whether the same file is an archive takes 0.0002 ms with the probe against 0.0801 ms for `Archive::from_bytes`. The probe numbers are tenths of a microsecond, which is the resolution the harness works at: read them as "this is not work". The python `has_manifest(path)`, which does read the file, is 0.005 ms against 0.434 ms for `Archive.from_bytes` over the same file, and the file never enters python memory.

The other three are not about time. `set_entry_format` removes an inflate and a deflate of a member whose content does not change. `reorder_entries` gives a host the order of the written archive, which it had no way to set. The exception classes remove string matching from error handling: a host was deciding between `KeyError` and `ValueError`, and recognizing a wrong password, by the prefix and the words of a message.

## Upgrading

Nothing has to change for a caller. Every call is an addition, no behaviour of an existing call changed, and no message changed.

Two things are worth changing by choice:

- An `except OmexError` or `except ValueError` keeps working, and a handler which matched on the text of a message can now match on a class instead.
- In Rust, a wrong or missing password is `OmexError::Password` rather than `OmexError::Refused`. Its message still begins with `refused: `, so code which reads the message is unaffected; code which matches the variant exhaustively gains an arm. On the WebAssembly wire this is the fifth kind, `password`, next to `malformed`, `refused`, `unsupported` and `not_found`.

## One thing to know

`has_manifest` answers a structural question, which is not the question whether an archive can be opened. A container whose manifest is encrypted answers `True`, because the manifest is declared whether or not the caller may read it, and so does one holding a member name `from_bytes` refuses. A file which is no zip container answers `False` rather than raising, as `zipfile.is_zipfile` does; a file which cannot be read is an `OSError`, because being unable to read a file is not an answer about its content.

`head` is a prefix, so neither the CRC32 nor the uncompressed size from the central directory is checked: both describe the whole member. Nothing is cached, so a later `entry_bytes` inflates as it would have.

## Limitations

Unchanged from 0.2.0. A write still builds the whole archive in memory, so writing a multi-gigabyte archive needs that much memory; the probe is the one question which is now answered without it. The reader's inflate budget is 1 GiB per member and an expansion ratio of 1032, and `head` is bounded by its own limit instead, so a member too large to inflate whole still has a head.
