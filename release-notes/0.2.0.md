# pymetadata-core 0.2.0

Three read-only calls on the python `Archive`, none of which inflates anything (`members` reads the central directory, which is already parsed when the archive is opened):

- `Archive.members` lists the members of the source container as `(location, compressed size, uncompressed size, method)` tuples, in zip order. It describes the container the archive was opened from and nothing else: it is empty for `Archive()`, and neither grows with `set_entry` nor shrinks with `remove_entry`. It includes `./manifest.xml` and members the manifest does not list, such as `__MACOSX` entries, and excludes directory members and `.`. A name which occurs twice in the container appears once per member.
- `Archive.has_bytes(location)` tells whether a location has bytes, either in the container or staged by `set_entry`. It is false for `.`, for `./manifest.xml` and for a declared entry which no member provides.
- `Archive.declared_entries` returns the entries exactly as the `manifest.xml` of the container declared them: in document order, with no entry invented for a member the manifest does not list, no required entry prepended, and duplicates as parsed. It is fixed when the archive is opened, so `set_entry` and `remove_entry` do not change it.

## Why

The python package `pymetadata` is replacing its own OMEX implementation with this core while keeping its public behaviour. That behaviour drops a manifest entry which no member provides, and appends the members the manifest does not list, sorted by location. Reproducing it needs a way to tell an entry the archive declared from one the core invented, and a present entry from an absent one, without inflating a single member.

0.1.0 had no such way. `entry_bytes` inflates, and `entry_bytes("./manifest.xml")` is refused by design, so the declared manifest could not be recovered. A real case is `iCGB21FR.omex`: its manifest declares 8 entries, one of them without a member, while the archive holds 22 members, so `Archive.from_bytes` yields 24 effective entries.

## Upgrading

Nothing has to change for a caller: the three calls are additions and no existing behaviour changed.

## One thing to know

`entries` holds the entries the core makes effective, which include the ones it invented for unlisted members. `declared_entries` does not. For `iCGB21FR.omex` the first has 24 items and the second 8. Use `declared_entries` when the question is what the archive said, and `entries` when it is what the archive will contain once written.

## Python only

These calls exist in the python package only. The WebAssembly host and the npm package keep the 0.1.0 surface unchanged, a deliberate asymmetry recorded in `docs/design/omex-core.md`. Nothing else changed: reading, writing, the formats and the limitations listed in the 0.1.0 notes are as they were.

## Install

```bash
pip install pymetadata-core
npm install pymetadata-core
```
