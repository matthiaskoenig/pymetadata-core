# pymetadata-core 0.4.0

A write which does not hold the archive it writes.

- `Archive.to_path(path, recompress=False, level=9)` writes the archive to a file, member by member, and returns the number of bytes written. The file holds the bytes `to_bytes` returns for the same content.
- In Rust, `Archive::write_into(sink)` and `Archive::write_into_recompressed(sink, level)` write into any `std::io::Write`. `to_bytes` is the same call with a `Vec<u8>` as the sink.
- `OmexError::Io`, kind `io` on the wire, is a sink which did not take the bytes. The python binding raises it as an `OSError`.

## Why

`to_bytes` built the whole archive in a `Vec`, and the binding copied that `Vec` into a `bytes` object, so writing an archive to a file cost the archive twice on top of the container the reader holds. The writer which this core replaced in `pymetadata` streamed into the file and never held more than one member.

A COMBINE archive of 268.5 MB with one incompressible member, opened with `from_bytes`, which leaves the process at 525.7 MB. Peak RSS of the process and the wall clock of the call, one run, python 3.14, the machine of `BENCHMARKS.md`:

| write | peak RSS it adds | time |
|---|---|---|
| `to_path` | 0.0 MB | 46 ms |
| `to_bytes` plus `Path.write_bytes` | 256.5 MB | 163 ms |

The streamed write is faster as well, because the bytes are copied once into the file instead of into a `Vec`, then into a `bytes`, then into the file. End to end through `pymetadata`, reading and writing the same file, the peak falls from 810.4 MB to 553.5 MB.

## Upgrading

Nothing has to change. `to_bytes` is what it was, byte for byte, and no message and no behaviour of an existing call changed.

Two things are worth changing by choice:

- A host which writes a file should use `to_path`, which is the whole point of the release. A host which wants the bytes, the WebAssembly host among them, keeps `to_bytes`.
- A caller which catches `OmexError` around a write should know that a failed write is now an `OSError` and not an `OmexError`: it was impossible before, since a write into memory does not fail that way.

## One thing to know

`to_path` creates the file, or truncates it if it is there, and a write which fails part way leaves what it had written behind, as a failed write of a file does. A caller which needs the file to be the archive or nothing writes to a temporary file in the target directory and moves it, which is what `pymetadata.omex.Omex.to_omex` does.

## Limitations

The read is unchanged and is now the whole of what an archive costs in memory: `from_bytes` takes a slice and copies it, so an opened archive holds its container, and a python host holds the `bytes` of the file as well. For the archive above that is the 525.7 MB the measurement starts from. Removing the copy, and reading a container without holding all of it, are [#14](https://github.com/matthiaskoenig/pymetadata-core/issues/14).

The inflate budget of the reader is unchanged: 1 GiB per member and an expansion ratio of 1032, with `head` bounded by its own limit instead.
